# Tag Steam's hover cards through own-host candidates and store layers

## Context and problem statement

Steam shows a game's hover card when the pointer rests on its capsule. Two shapes exist, captured on 2026-11-15 with the dev bundle injected:

- Classic pages (search, bundle, curator, home) fill `#global_hover_content` with one `div#hover_app_<appid>` per hovered game. A later hover of the same game only switches the blocks' `display`. The block holds no app link and no `data-ds-appid`, and some blocks hold no image. No candidate in `src/core/scan/candidates.ts` names its app, and the scanner never sees the card.
- React pages (tag hubs, category and sale hubs) mount a full-viewport `div[popover="manual"]` inside the hovered capsule's `[data-key="hover div"]` on each hover, and unmount it when the pointer leaves. Its links name the same app as the capsule around it. `knownHostAround` climbs from the card into the capsule's host and folds the card into it, which leaves the card without chips. The card also sits before the capsule's own image, so the capsule's first image is a screenshot in the card.

Rule 11 keeps the scanner closed to new surfaces, and both cases need the scan to read something new. How should the scan reach both cards?

## Decision drivers

- Rule 11: a new surface is an entry in a list, and the next one needs no scanner edit.
- Rule 13: no polling, only added subtrees, no request for a cached verdict, no listener per node. A React card mounts again on every hover.
- Rule 4 and the native look: the card keeps Steam's own words and layout around our chips, and nothing Steam drew moves.

## Considered options

1. Two seams in the scan: candidate sources and own hosts in `candidates.ts`, and store layers in `layers.ts` that every ancestor walk stops at (chosen).
2. Hard-code both cases: add `[id^='hover_app_']` to the scanner's selector loop and `[popover]` to `knownHostAround`.
3. A pointer listener or a second observer that tags the hovered game's card on its own.

## Decision outcome

Chosen option 1.

- `CANDIDATE_SOURCES` in `candidates.ts` is what a scan lists in each added subtree: `OWN_HOST`, then app links. `OWN_HOST` joins `[data-ds-appid]` and `HOVER_CANDIDATE` (`[id^='hover_app_']`). `namingOf` reads a block's app from its id through `appIdFromHoverId`, and `hostOf` takes an `OWN_HOST` element as its own host, as it did for `data-ds-appid`.
- `LAYER_ATTRIBUTES` in `layers.ts` lists store layers by the attribute on their root; the first is `popover`. Every ancestor walk steps through `layerParent`, which stops at a layer root: `knownHostAround`, `enclosedByFresh` and `holdsKnownHost` (through `sameLayer`) and the candidate a root sits in, in `scanner.ts`; `parentOf` in `hosts.ts`; and `firstImage` in `image.ts`, which skips an image in a layer inside the host. A host or a capsule image inside a card and the capsule's host around it never join, in either direction.
- A scan waits `DEBOUNCE_MS` (200 ms) after the last added node, which would draw a card's chips a moment after the card. When an added node opens a card (`opensCard` in `candidates.ts`: a layer root or a classic app block), the scan runs in the next frame instead, so the chips paint with the card. Other additions keep the debounce, which batches GetItems requests while a list streams in.
- Two placements. `hover-card` puts a full badge at the end of the classic block, under the user tags. `hover-layer` (`[popover], [popover] *`) puts one at the end of the React card's info block, under the tags, the reviews and the release line. Both show every chip (`CARD_CHIPS`): no pointer reaches the classic card to open a "+N" chip. Neither hides.
- The classic card is a light ground. Its chips take the compact badge's solid surface and light text: 12.65:1 on that surface, and 11:1 or more between the surface and the card. Forced colors override them as they do every chip. They sit `tks-space-2` under the user tags, a line of their own, so they never read as more user tags. In the React card they sit `tks-space-1` apart, as the store's tags there do.
- One rule keeps the list filter's dim off both cards. A card shows the one game the pointer rests on, and the dim's own `:hover` rule cannot lift it, because the pointer stays on the capsule.

### Library check (rule 12)

Nothing adopted. The change reads ids and attributes through DOM calls the scan makes today.

### Consequences

- Good: a later store layer or an element that names its app without a link is one entry. The scanner, the host finder and the detector chain stay as they are.
- Good: the chips paint with the card. Measured live on 2026-11-15, they landed 1 to 2 ms after a classic block and 4 to 8 ms after a React card's mount, both before the next paint.
- Good: hovering a classic card's game again changes only the blocks' style, which no scan reads. A React card's new mount costs one scan of its subtree and a draw from the cache, with no GetItems request.
- Good: the capsule's host no longer counts as changed when its React card mounts, and skips a redraw on each hover.
- Bad: each placement costs one `matches` call per new host. The page scan budget in `scanner.test.ts` now allows 16 calls per capsule; the scan makes 14.
- Bad: the card grows by one line under Steam's content. Nothing above the chips moves. Steam's script places the classic card from the height it measures; near the viewport's bottom edge, where Steam opens the card above the capsule, the chips' line may reach past the edge. The smoke runs did not show it.
- Bad: `popover` is a generic HTML attribute. Every store popover becomes a layer, and every host inside one takes the `hover-layer` placement with all its chips. The store's hover card has no stable class (`docs/design/components.mdx`), and the captured pages show no other popover with app links. Revisit when one appears, and narrow the layer and the placement to the card's shape then.
- Neutral: the content bundle grows to 255,850 of its 256,000 bytes.

### Confirmation

`scanner.test.ts` pins both captured shapes in `tests/fixtures/surfaces/hover-card/`. Each classic block is a host with its chips at the end, and a new block gets a host of its own in the next frame. The React card is a host apart from its capsule's, the capsule keeps its own image as its anchor, and each new mount gets a host in its frame, with one root and no changed host. With the layer boundary, the image boundary or the next-frame scan turned off, these tests fail. `app.test.ts` draws every chip in the classic card from one GetItems request, and the React card's chips on each mount with no further request. `list-filter.test.ts` keeps a host in either card undimmed under Dim and Hide. On 2026-11-15 the dev bundle drew the chips in the classic card on the search page, in the isolated world and in the page world beside Prototype.js 1.7, and in the React card on the Roguelike tag hub and the Action category hub.

## Pros and cons of the options

### 1. Candidate sources and store layers (chosen)

- Good: both seams are data, as `NESTED_PLACEMENTS` is (ADR 0025).
- Good: `opensLayer` adds one attribute read to ancestor walks the scan makes today, and no selector query.
- Bad: one scanner edit now, recorded here.

### 2. Hard-code both cases in the scanner

- Good: the smallest diff.
- Bad: the next layer or id-named element edits the scanner again, which rule 11 rules out.

### 3. A pointer listener or a second observer

- Good: it could draw before the scan's debounce ends.
- Bad: a second detection path beside the scanner and the capsule UI, with its own listener or observer and its own draw code.
